# Storage policy on the existing OGT server

Only new uploads are processed. Previously published media and editing originals are not recompressed or removed.

- Images retain the established 2048 px maximum edge, EXIF rotation, transparency, animation and metadata privacy behavior. No additional lower-resolution variants are stored.
- Ordinary new videos have a 120 second maximum; the native editor lets the author choose the range. Stories keep their 30 second maximum. Existing remote videos are not forced through a new upload when a post is edited.
- The web editor previews a local file and sends it only after confirming the selected range. Its temporary source is limited to 12 MiB, serialized on the server and removed after encoding. Only the verified selected MP4 (up to 8 MiB) is stored. Larger originals can be trimmed locally in the native app. This avoids Safari's recording-clock gaps.
- A single server encoder at a time uses one thread, H.264/AAC, a 1280 px bounding box, variable quality and fast-start MP4. Successful optimization retains duration, aspect and audio stream count. Already-compatible MP4 files are only replaced when smaller; WebM is normalized to MP4 for Apple playback when possible, within the same 8 MiB ceiling. Unsupported color/extra track cases keep the complete source. Timestamp rounding allows at most 100 ms at the two-minute boundary.
- SHA-256 deduplication uses hard links within separate public/private media namespaces. Every upload retains a distinct UUID, URL, ownership record and independent revocation. Deleting one reference cannot remove another upload. The final physical copy is collected when its last alias is deleted. No existing media is migrated.
- New ordinary posts expire from the feed 90 days after creation, not from their source publication date. They remain in profiles, direct links, adoption applications and conversations. Existing posts have no expiry assigned. Owners can renew for another 90 days from their detail page. Expiry is not content deletion and does not save media bytes.
- Every expiry period gets one durable inbox notice and at most one push attempt during its final 24 hours. A unique database key prevents duplicate claims across workers/restarts. Renewing creates a new expiry period. Notification settings, quiet hours and device permissions still apply; there is no guaranteed push receipt when a device is offline. The inbox notice remains available.
- Existing scheduled database snapshots continue their verified 30 day rotation. Database snapshots from deployments also keep 30 days; redundant application archives follow the five-version/48-hour release policy. A recent hash-verified database backup and successful PostgreSQL archive inspection are required before either operation.
- Release rotation keeps the five newest packages, every package under 48 hours, the active SHA and explicit IDs in `operations/retention-pins.json`. Only manifest-verified packages qualify. Manual/unknown/changed/symlinked material is preserved. Exact-file audit inventories are saved before deletion. Media, the database, Docker volumes, environment files and unrelated server applications are outside the rotation.
- The same rotation removes only exact expired `ogt-backend:<release>` / `before-<release>` image tags. Images referenced by any container or retained/manual recovery material are protected. It never uses force or global Docker pruning and leaves other projects' images untouched.
- Rotation holds the existing release and backup locks and checks API health. Daily execution is installed in the existing named OGT cron block, preserving unrelated jobs. The default retention command is a read-only plan; `--apply` is explicit.

Before applying on the VPS: run unit and integration checks, review the plan, preserve a current backup and compare protected content/ownership references after deployment. No external storage subscription is required.
